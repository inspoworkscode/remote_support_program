What this product is, in three sentences

  1. It is a remote support tool, like TeamViewer or AnyDesk. An IT technician can see and control a customer's Windows computer over the internet, with the customer's permission.
  2. It is also a job and ticketing system for an IT business: customers, their machines, workshop bookings, quotes, invoicing stages, photos, and staff chat.
  3. It is sold to other IT companies — and other businesses that look after other people's computers and jobs — as an online service. Each company gets its own branded copy (its own logo, colours and download links), and all of them run on one shared server at https://theremotesupportprogram.com. The Basic Version for Remote Workers (R50 a month since 2026-10-25) lets one person reach up to three of their own computers (more at R10 each, up to 20), for example the office PC from home, attended or unattended; the Free Version does the same for ONE computer, unattended, for nothing. Both can be upgraded in place.

Every part of it was written from scratch for this business. No remote-control engine was bought in or licensed, so there are no licence fees and nobody else's code to depend on.

The company that owns it is The Remote Support Program (Pty) Ltd, registration 2026/737434/07 (South Africa). Its first customer is Anywhere IT, Clint's own IT company.

The three things most likely to cause damage

  1. Losing the server's key folder (data/keys). It unlocks every stored workshop device password and email password. The nightly backup contains it (and an office PC can fetch a copy every night — deploy/backup/README.md; check it is switched on), but the backup itself is locked with a passphrase kept in /etc/rsp-backup-key on the server. Both must be kept safe — see 08.
  2. Changing the setting called SetApplicationName("RemoteSupportPlatform") in the server's Program.cs. It looks harmless. Changing it makes every stored password unreadable.
  3. Turning off two-factor sign-in on the live server. It is switched off only inside test tools. A technician's password, without the second factor, would be enough to reach every customer machine of that company.

On the customer's computer (three programs)

  • The tray app (RemoteSupport.Client). The small icon by the clock. The customer uses it to ask for help, chat, choose whether unattended access is allowed, set an unattended password, let somebody outside their IT company in with a code, and uninstall the whole product. It also asks the customer's permission before a technician connects. **A free-version computer has no tray app** — the same file is used only to install and set the password.
  • The agent (RemoteSupport.Agent). A Windows service that runs in the background all the time, even when nobody is logged in. It is what makes unattended access possible, it installs and removes the monthly health check, and it uninstalls itself if the IT company removes the machine while it is online.
  • The host (RemoteSupport.Host). Started fresh for each session and closed afterwards. It does the real work: takes pictures of the screen, presses keys and moves the mouse, copies files, runs scripts, captures sound, adds the technician's printer. It runs with full system rights so it can also work on Windows' secure screens (the password prompt, Ctrl+Alt+Del, the lock screen). On a free-version computer it also shows the "Being controlled remotely" bar for the whole session.

On the technician's computer (one program)

  • The technician console (RemoteSupport.Technician). The list of customer machines, the incoming-call alert, the session window (where the customer's screen appears), chat, tickets.

The server (one program)

  • The platform (RemoteSupport.Platform). A web server that does several jobs at once:
    1. The public website — marketing pages, download pages, website chat.
    2. The portals — the web pages office staff use for tickets, clients and settings, and the owner portal.
    3. The hub and relay — every program above connects to it. It rings technicians when a customer asks for help, and during a session it passes the screen picture one way and the mouse and keyboard the other. It does not store the screen picture. It just passes it on.
    4. The database — companies, staff, customers, machines, tickets, photos, chat history. On the live server it is PostgreSQL (since 9 October 2026), on a disk of its own; a developer's PC and most test tools use SQLite, a database in a single file, and the code works on both.
    5. Payments — card payments through PayFast, and the owner pages with the control dashboard (V2.2).

There is also an older program, RemoteSupport.Server, from before the product served many companies. It is kept but no longer used live. Leave it alone unless you are removing it.

Shared libraries (no program of their own)

  • RemoteSupport.Shared — the "language" all the programs speak to each other, plus things every program needs (security rules, the two-factor code maths, device identity).
  • RemoteSupport.UI — the look of the Windows programs (rounded buttons, colours, light and dark).
  • RemoteSupport.Media — video and sound: turning the screen into compact video (H.264), playing it back, recording sessions, the microphone with echo cancelling.

How a support call works, step by step

  1. The customer clicks Request Support in the tray app and types what is wrong.
  2. The tray app tells the server. The server rings every technician at that IT company who is signed in. A large alert appears in the middle of each technician's screen, even if the console is minimised and the sound is off.
  3. A ticket is opened automatically with the customer's description.
  4. The first technician to click Accept gets the call.
  5. The server tells the customer's computer to start a host. The host connects to the server.
  6. The customer sees a permission prompt ("Allow a remote support connection?"). If nobody answers in time, the answer is no.
  7. Once allowed, the technician sees the customer's screen and can use the mouse and keyboard. Other technicians can join the same session.
  8. When the session ends, the ticket is updated with what happened (who connected, chat, files, scripts run, how long it took).

Unattended access is the same, except the technician starts it from the machine list, and the customer is not asked each time — because the customer has ticked Allow unattended access in their tray app. If the machine has an unattended password, the technician types it once and it is remembered for them. More in document 02.

On the Free and Basic versions there is no call: the one person picks one of their computers, types its password the first time, and is in — or, on Basic, connects to one without a password and the person there is asked. The computer shows Being controlled remotely by … at the top of its screens while they are.

How the programs talk

  • Everything travels over one secure web connection (HTTPS and secure WebSockets on port 443). Nothing needs a special port opened on the customer's network: every program dials out to the server, the way a web browser does.
  • There are three kinds of connection on the server:
    • /ws/device — each customer computer (the tray app and the agent) keeps one open.
    • /ws/tech — each signed-in technician console keeps one open.
    • /ws/session — one for each live session, for the host and each technician viewing it.
  • Messages are small pieces of JSON text. The screen picture, file contents and sound are sent as compact binary pieces. The definitions are in src/RemoteSupport.Shared/Protocol.cs.

How one server serves many IT companies

  • Each IT company has a tenant key: a long random code built into its downloads. When a customer computer connects, it shows this key, and the server knows which company it belongs to. The key is an address, not a password — it is public by design (see document 03).
  • Inside the server each company gets its own separate hub in memory. Companies cannot see each other because they are not in the same place at all. The hub also knows whether its company is on the free version, and applies those limits itself (Hub/TenantHub.Free.cs).
  • Every company downloads the same program files. Only the branding file (name, colours, logo, server address, tenant key) is different. That is what makes one code-signing certificate cover every reseller.

02 — Every feature, and how it works

Each feature has three parts: what it does, how it works in plain terms, and where it lives in the code (for developers). A mark after the title says how far it has been proven:

  • [Proven] — used on real computers and confirmed working.
  • [Built] — written and passed its automatic tests, but **not yet tried on real customer computers**. Treat these as "probably works, needs checking". The checklist is docs/TEST-3.6.md.

Document 07 has the full picture of what is proven and what is not. "V2" after a mark means it was added between V1 of this pack (2 October 2026) and V2 (6 October 2026) — document 10 lists them all; "V2.1" (or "after V2") means it was added on 7 October 2026 — document 11; "V2.2" means it was added between 8 and 15 October 2026 — document 12; "V2.3" on 16 October 2026 — document 13; "V2.4" between 17 and 27 October 2026 — document 14; "V2.5" on 28 October 2026 — document 15.

Part A — Remote control

A1. Seeing the customer's screen [Proven]

What: The technician sees the customer's screen live, on any of their monitors, docked in the console, in its own window, or full screen.

How: The host takes a picture of the screen many times a second using Windows' own fast screen copy (Desktop Duplication). It compresses the pictures into video using H.264 — the same compression as online video — using the computer's graphics chip where it can. Only what changed is sent. Scrolling a document went from 2.8 MB per second to under 0.2 MB per second when this was added. If a computer cannot do H.264, it falls back to an older method (small JPEG squares of the parts that changed), so it still works, just using more data.

Automatic quality: if the internet line is struggling, the host lowers the picture quality and frame rate on its own, and raises them again when the line recovers (LinkController).

Fixed 6 October (V2): on computers whose graphics chip converts colours for the compression, a program opened or closed sometimes did not appear until the technician pressed Refresh. The converter was asked for its result only once per picture; it is now asked until it has finished (Media/GpuColourConverter.cs, HANDOVER.md §99). Not yet seen on the affected machine.

A picture that never stays blurry (V2.2, Built): on one test machine the picture arrived blocky and never became clear. Two causes: an automatic "start again" picture every 24 frames threw the sharpened picture away, and nothing sharpened a screen that had stopped changing. Now those pictures are a minute apart, and a still screen is encoded again for two seconds after any real change so it comes out sharp (Host/StillRefiner.cs). A blinking cursor does not count as a change. When the server has to drop a picture for a slow technician, it asks the customer's computer for a fresh one. Found on the way: a Windows structure had been read wrongly since September (HANDOVER.md §142).

Where: Host/DxgiCapture.cs, Host/ScreenCapture.cs (fallback), Media/H264Encoder.cs, Media/H264Decoder.cs, Technician/ScreenView.cs.

A2. Mouse and keyboard [Proven]

What: The technician's mouse and keyboard control the customer's computer, including on several monitors, and the customer's real mouse pointer shape is shown.

How: The console sends each mouse movement and key press to the host, which "presses" them on the customer's computer using Windows' input function (SendInput). Because the host runs with full system rights, this also works on programs running as administrator, on Task Manager, and on Windows' password prompts (UAC) and the lock screen.

Windows shortcuts (added 2026-10-07, after V2; Built): while the picture has the keyboard focus, the Windows key and its shortcuts, Alt+Tab, Ctrl+Esc, Ctrl+Shift+Esc, Alt+Esc and Print Screen act on the customer's computer, not the technician's. Windows keeps these keys for itself, so the console uses a keyboard hook that exists only while the picture is focused and takes only those keys. Ctrl+C, Ctrl+V and every other key travel exactly as before. There is no on/off switch. Win+L and Ctrl+Alt+Del cannot be taken by any program; the toolbar has buttons for both. Handover §110.

Where: Host/InputInjector.cs, Host/DesktopFollower.cs, Host/CursorShape.cs, Technician/ScreenView.Shortcuts.cs.

A3. Several technicians on one session [Proven]

What: More than one technician can watch and help in the same session.

How: The server simply sends the picture to every technician watching and passes every technician's input to the host.

A4. Surviving a dropped connection [Proven]

What: If the internet drops briefly, the session reconnects on its own.

How: The console keeps retrying for two minutes; the server keeps the session waiting for 90 seconds. If the line comes back in that time, the session carries on.

Where: Technician/SessionLink.cs, the hub's grace period in Platform/Hub/TenantHub*.cs.

A5. System buttons [Proven]

What: From the session toolbar: Ctrl+Alt+Del, Lock the machine, Open Task Manager, Restart the machine (and reconnect automatically after it comes back).

How: The host carries these out with system rights. Ctrl+Alt+Del needs a Windows policy setting, which the customer installer switches on.

A6. Copy and paste, both ways [Proven]

What: Text, files and whole folders copied on one computer can be pasted on the other, in either direction, as if both were the same computer.

How: Text is simply sent across. Files are different: when you copy a file, Windows only remembers where it is, not its contents. So the product first sends the file contents across, then tells the other computer's clipboard where the copy landed. Pasting then works normally in Windows Explorer.

A small helper program running as the logged-in person (not as the system) does the final clipboard step on the customer's side, because Windows Explorer refuses to paste a file list put there by a more powerful account. This took several days to discover and is written up in HANDOVER.md §39 and §40.

Privacy: the clipboard is only shared while a technician is connected, and stops the moment they leave.

Every movement is written on the ticket (what, which way, how big, when) [Built].

Where: Host/ClipboardAccess.cs, Host/UserProcess.cs, Shared/FileSetTransfer.cs, Shared/ClipLedger.cs.

A7. Moving files: drag and drop, and the Files window [Proven, drag-off-the-picture Built]

What:

  • Drag a file or folder from the technician's desktop onto the customer's screen — it lands on the customer's desktop. [Proven]
  • The Files window shows the customer's drives and folders; drag files out of it to the technician's computer. [Proven]
  • Drag a file straight off the picture of the customer's desktop onto the technician's desktop. The product reads what the customer has selected in Explorer. [Built]

How: Files are sent in small pieces (64 KB). Every received path is checked so a file can never be written outside the folder it was meant for (this blocks a known type of attack). The customer is told in plain words what was moved.

Where: Host/FileTransfer.cs, Host/ExplorerSelection.cs, Technician/DragOut.cs.

A8. Running scripts [Proven]

What: The technician can run a PowerShell or batch script on the customer's computer and watch the output appear live.

How: The host saves the script to a temporary file and runs it with system rights, sending back each line of output and the final result code.

Where: Host/ScriptRunner.cs.

A9. Hearing the customer's computer [Proven]

What: Listen plays the customer's computer sound on the technician's speakers. The Sound window explains why there is no sound on the customer's machine (muted, wrong speakers chosen, driver problem) instead of leaving the technician guessing.

Where: Host/AudioCapture.cs, Host/AudioDiagnostics.cs, Technician/AudioPlayer.cs.

A10. Talking to the customer, both ways [Built]

What: Talk to the customer sends the technician's voice to the customer's speakers. The customer is asked whether to use their microphone too — every session, and never for unattended sessions. Echo cancelling is used at both ends.

Where: Host/VoiceCall.cs, Media/EchoCancelledMic.cs, Technician/SessionForm.Voice.cs.

A11. Privacy screen [Built]

What: Blanks the customer's monitors (they see black) while the technician still sees and works normally. Useful in open offices.

How: Black windows that Windows is told to leave out of screen capture. If it cannot work properly on that computer, it refuses rather than half-working, and says so.

Where: Host/PrivacyScreen.cs.

A12. Recording a session [Built]

What: Tools → Record this session. A red marker shows while recording. The video is saved by the technician's console and uploaded to the session's ticket. Only someone in the session can attach one; only a supervisor or the owner can delete one. The customer is told.

Where: Media/ScreenRecorder.cs, Technician/SessionRecorder.cs, Platform/Services/RecordingService.cs. Recordings are stored in the server's data/recordings.

A13. Session chat and the Info window [Proven]

What: Chat with the customer during a session (it pops up on their side and can be moved). Info shows the customer computer's details: Windows version, processor, memory, disk, and which account the host is running as.

A14. Remote printing, both ways [Built — V2]

What: Tools → Print on my printer: a printer named after the technician (for example "Sue Tech's printer") appears on the customer's computer, and whatever the customer prints to it comes out on the technician's own printer. Tools → Print a file on their printer…: the technician picks a file and it prints on the customer's default printer.

How: No printer driver of ours: the added printer is Windows' own Microsoft Print to PDF writing to a file, which the host picks up and sends to the console, which prints it. The printer is removed when the technician leaves the session. Known limit, said to the technician: two documents printed within a moment can arrive as one.

Where: Host/PrintRedirect.cs, Technician/SessionForm.Print.cs, Media/PdfPages.cs. HANDOVER.md §95.

A15. Wake-on-LAN [Built — V2]

What: Right-click an offline machine → Wake up. Another of that customer's machines on the same network sends the wake-up signal — nothing to set up on the customer's router. The technician is told which machine sent it, or why it could not be sent.

Where: Platform/Hub/TenantHub.Wake.cs, Shared/WakeOnLan.cs. HANDOVER.md §94.

A16. "Being controlled remotely" [Built — V2, the Free and Basic versions only]

What: On a Free or Basic computer, which has no tray app, a small amber bar at the top centre of every monitor says Being controlled remotely by … for the whole session, naming who is connected.

How: Like the privacy screen, the bar is left out of screen capture, so it is on the person's screen but not in the technician's picture, and clicks pass straight through it.

Where: Host/ControlledNotice.cs. HANDOVER.md §104.

A17. Two machines at once, and copying straight between them [Built — V2.2]

What: A technician can have two sessions open side by side, one per monitor — two at most (Shared/SessionLimit.cs; the console refuses a third before asking, and so does the server; reconnecting to one already open never counts). Copy on one machine, paste on the other: files copied on machine A are held, and when the technician clicks into machine B's window and pastes, the server joins the two sessions for that one copy and A's computer sends the files straight to B's — through the server, but never through the technician's PC or line. A key made for that copy is handed to each machine inside its own sealed session, so the server cannot read the files. If an older program is involved, or the server says no, the files go through the technician's PC as before.

Where: Platform/Hub/TenantHub.Bridge.cs (BridgeProblem is the one rule), Host/HostEngine.Bridge.cs, Shared/BridgeSeal.cs, Technician/SessionForm.Bridge.cs, SessionForm.Between.cs. HANDOVER.md §143–144.

Part B — Access and permission

B1. Asking for help (attended support) [Proven]

What: The customer clicks Request Support in the tray app and must say what is wrong. Every signed-in technician at that IT company is rung. The reason is the biggest text on the alert.

How: The alert is always on top, flashes the taskbar, and never steals the keyboard from whatever the technician is typing. The first to accept gets the call.

Since 9 and 13 October (V2.2, Built): the request has a short subject and an optional description, and a tick to send a picture of the screen, previewed first, which lands on the ticket. The app remembers the customer's name (per Windows user). Because customers usually minimise everything to reach the desktop shortcut, the picture often showed only the desktop: the window now says so, and Take a new picture hides it while they bring the right window up. It never restores their windows for them, on purpose (Client/ScreenSnap.cs, Client/LastContact.cs, §122 and §129).

Since 18 and 23 October (V2.4, Built): the name typed into a request names the machine while it is not linked to a client — shown in grey italic in the console and the portal instead of DESKTOP-ABC123, the latest name winning — and linking it offers that person as a contact (Shared/OwnerNames.cs, §150). The installer asks who the computer is for (name, surname, email) and that does the same from the start; the server keeps it once per install, so a later request's name still wins (Shared/GivenPerson.cs, §156).

Where: Client/RequestDialog.cs, Technician/IncomingCallPopup.cs.

B2. The permission prompt (consent) [Proven; the system-level version Built]

What: Before anyone sees the customer's screen in an attended session, the customer sees a branded prompt naming the technician. If nobody answers within the time limit (60 seconds by default), the answer is no.

How: The host connects to the server first but does nothing at all until the customer says yes. The technician sees "Waiting for … to accept" with a countdown and a Cancel button.

Since 16 October (V2.4, Built): the prompt comes to the front and stays there. Windows takes the always-on-top mark off a window a background program shows, so it used to open behind whatever the person was using (UI/ComeForward.cs, §149).

Where: Host/ConsentPrompt.cs, Technician/ConsentWaitForm.cs.

B3. Unattended access — a switch the customer holds [Proven]

What: A technician can connect without anyone at the computer — but only if the customer has ticked "Allow unattended access" in their tray app. They can untick it at any time.

C6. Keeping itself up to date [Built — V2.3]

What: Every program on a customer's computer — the tray app, the background service, the program that does the work in a session, the install scripts and the health check — updates itself when we release a new version, and so does the technician's console. Nobody at the customer's computer is asked (Clint's decision).

How: Every build carries a version made from the moment it was built (2026.10.16.1432 is 14:32 UTC on 16 October 2026), shown in the console, the portal's Devices page and the control dashboard. A new release goes to our own company's computers first; a Full admin or Owner moves it on to the pilots, then everybody, on Owner → Updates, and can pause it. The server offers it to a few computers a minute. Each computer:

  1. downloads it from its IT company's own server;
  2. checks every file is signed by us, not revoked, and newer than what it has — anything else is refused, and that version is never taken again;
  3. waits until nobody has been connected for 10 minutes;
  4. swaps the files (a running program is renamed aside, never overwritten; only the release's own files are touched — never the computer's identity, branding or settings) and restarts its service;
  5. keeps the new version only if it connects back within 5 minutes; otherwise it puts the old files back by itself. A computer that rolls back pauses the release for everybody and emails the admins.

The console checks before its sign-in window and restarts itself in the new version; while open, it shows Update ready.

Computers installed before 16 October need one update by hand — connect, then Tools → Scripts → Update this machine — after which they update themselves. The portal's Devices page counts and marks them.

Seen on hardware (19 October, V2.4): the background services updated themselves — one PC took four releases, about 20 seconds each, with no rollback. The tray app never followed: Windows answered "what version is this file?" from the copy already running, so the tray app read the new file as its own old one. It now reads the file itself (UpdateTrust.FileVersionOnDisk — never ask Windows for the version of a file a program started from). Tray apps already running in the field are the old code and cannot notice: each computer needs one sign-out or restart after that deploy, then follows by itself. tools/updatestate.ps1, run on a computer through Scripts, says why it is behind (§152).

Where: Shared/AppVersion.cs, UpdateTrust.cs (the signature check), UpdateRunner.cs, UpdateSwap.cs, UpdateByHand.cs; Agent/AgentUpdate.cs; Technician/ConsoleUpdate.cs; Platform/Services/UpdateService.cs (every rule of the rollout), UpdateSweep.cs, Pages/Owner/Updates.cshtml; tools\BuildVersion.ps1. Part F — Tickets and job routes

F1. Tickets open and fill themselves in [Built]

Every remote session gets its own ticket automatically. Accepting a call assigns it. Connecting, chat, scripts, clipboard and file movements, and the session's end and length are all written on it. Bigger jobs can be made of several sessions (a "parent" ticket). Staff can also open tickets by hand.

Since 9 October (V2.2): linking a ticket to a bigger job no longer closes it — it stays open, is finished and closed on its own, and the bigger job cannot close until its parts are done (a pop-up names them; TicketService.ClosesJob, Shared/JobParts.cs). 03 — How the security works

A remote support tool can control customers' computers, so security matters more here than in most software. This document explains, in plain terms, what protects what, and is honest about what is not yet done.

The detailed engineering record is HANDOVER.md §72 (signing in), §73 (passwords), §31/§41 (unattended), §77 (unattended password) and §76 (permission prompts); since V2 also §100 (remembered unattended passwords), §101 and §105 (the free version's limits), §104 (Being controlled remotely) and §106 (removing machines, and Uninstall).

The one idea to hold on to

The thing that guards every customer computer is a technician's sign-in. A technician who is signed in can reach every machine of their company that allows unattended access, and scripts run there with full system rights. So most of the security below is about making sure only the real technician can sign in, that access stops immediately when it should, and that the customer stays in control of their own machine.

1. Everything is encrypted on the way

  • All traffic between every program and the server uses TLS 1.3 — the same protection as online banking. It was measured on the live server on 1 October 2026: TLS 1.3, with a key exchange that is designed to resist future quantum computers (X25519MLKEM768), and AES encryption.
  • The certificate comes from Let's Encrypt and is renewed automatically by Caddy, the web server that sits in front of the platform.
  • The programs refuse to talk unencrypted over the internet. If a program is ever pointed at a plain http:// address on the public internet by mistake, it refuses to connect. Unencrypted is only allowed on a private office network (for testing). This rule is in Shared/SecureTransport.cs.
  • None of the programs ever switches off certificate checking.

And end to end, since 7 October 2026 (HANDOVER §112, not yet seen on a real machine). TLS ends at the server, so before this a session was readable INSIDE the server — the picture, every key typed (passwords included), the clipboard, files, sound, scripts. Now the customer's machine and each technician's console agree a key the server never sees, and everything a session carries travels sealed with AES-256-GCM; the server relays it and cannot open it. Each machine has an identity key (made on the machine, readable only by the system) that signs the session key, and every console remembers it: if it ever changes — a reinstall, or somebody pretending — the console stops and asks before showing or sending anything. What the server still reads, on purpose: who connected to what and when, and the audit lines for the ticket (file names moved, a script's first line, reboots). Honest limit: a server that had been taken over could still START a session of its own; it could not read or hijack a real technician's. The session window says which it is — a green End-to-end encrypted, or Not end-to-end encrypted when an older app is involved. The design is docs/NEXT-SESSION-E2E.md.

2. Signing in

Passwords

  • Stored only as a one-way scrambled value (PBKDF2-SHA256, 600,000 rounds since 7 October 2026 — older ones are re-made at each person's next sign-in — a different random "salt" for each person). Nobody — not even someone with the database — can read a password back.
  • At least 8 characters and not the person's email address.
  • People choose their own passwords through an emailed link. Nobody types a password for someone else, so a supervisor never knows anyone's password.

Two-factor sign-in (2FA), for everybody

  • After the password, a six-digit code from an authenticator app on their phone (Google Authenticator, Microsoft Authenticator, etc.). This is the standard called TOTP.
  • Each code works only once.
  • Ten recovery codes are given once at setup, for a lost phone. Each works once. They are stored only as a scrambled value.
  • The code is asked once every 7 days on the same computer or browser; the password is asked every time. That "trusted for 7 days" token is tied to the person and is cancelled instantly by any password change, role change or sign-out.
  • A supervisor can reset someone's two-factor (they set it up again at their next sign-in).

Stopping guessing

  • 5 wrong attempts on one account → that account is refused for 15 minutes, even with the right password.
  • 30 wrong attempts from one internet address → that address is refused.
  • "Forgot password" gives the same answer whether or not the email exists (so it cannot be used to find out who has an account) and is limited to 3 emails an hour per address.
  • A sign-in from a new network is emailed to the person.

Being signed out at once when it matters

  • Every sign-in carries a security stamp. Changing a person's password, roles or two-factor, removing them, or pressing Sign out on the People page changes the stamp. Their console is closed within a second, and their web portal on the next page they open.
  • A console's sign-in expires after 12 hours unused.

One sign-in at a time (added 2026-10-05)

  • Each person can be signed in to one console and one web browser at a time. Signing in to the console on a second computer closes the first console; signing in on a second browser signs the first browser out on its next page. The person who was pushed off is told why.
  • Signing in on a different computer asks for the two-factor code even if that computer was trusted, and cancels the 7-day trust on every computer, so the first one is asked for the code too. This is in case the second sign-in was somebody else who has the password.
  • Signing in again on the same computer, or after pressing Exit or Sign out, asks for nothing extra. The console's Tickets button opens the portal without counting as a second browser.

Sign-in links

  • Invitation links last 72 hours, password-reset links 2 hours, and each can be used once.
  • A link is used up only when the new password is actually submitted, not when the email is opened (email scanners open every link).

The platform owner signs in with a long secret owner key and a separate authenticator code.

3. The customer stays in control

  • Permission before every attended session. The customer sees who is connecting and must click Allow. No answer within the time limit means no. Until they say yes, the program on their machine connects but does nothing at all — no picture, no input.
  • Unattended access is the customer's switch, in their tray app. Untick it and unattended access stops. Only the customer's own tray app can change it — not the server, not a technician.
  • An unattended password can be set on the machine by the person there. Then nobody, including the IT company's owner, gets in unattended without it. There is no office override, on purpose. Five wrong tries lock the machine for 15 minutes.
  • Remembered for each technician (V2). Once a technician has typed it correctly, it is not asked of them again. This loosens the rule above on purpose and only this far: every technician still has to type it once. The server keeps only that it was typed right, against which password — never the password or its scrambled form. Changing the password at the machine forgets it for everybody. Someone else guessing (and locking the machine) does not lock out somebody who already knows it.
  • Uninstall (V2). The person at the machine can remove the product themselves from the tray app; Windows asks for administrator permission. The IT company sees that it was uninstalled.
  • Only the machine's own tray app speaks for the person at it. The permission switch, the password, closing the app and uninstalling are all accepted by the server only from that connection — never from the agent service (which is what they guard) and never from a technician.
  • Exit in the tray app takes the machine fully offline for support.
  • The microphone is never opened without asking the customer in that session, and never in an unattended session. The server itself blocks any attempt by a technician's program to answer that question on the customer's behalf.
  • The customer is told when a technician connects, when files move, and when a session is being recorded.
  • The clipboard is shared only while a technician is connected.

4. What each person is allowed to do

  • Roles are Owner, Supervisor, Technician and Office administrator, as tick boxes.
  • Every permission check is done on the server, in one place (Platform/Services/Permissions.cs). Hiding a button is never relied on — the server refuses the action itself.
  • Office administrators cannot connect to any customer machine.
  • A technician never closes a ticket; "do not invoice" needs a supervisor.
  • Only a supervisor or the owner can delete a session recording.
  • Only a supervisor or the owner can remove a machine (V2), and it needs a reason. A removed install is refused if it ever comes back — it cannot quietly put itself back on the list. An online machine is told to uninstall itself; the instruction is sent only to its agent, only at that moment.
  • Only a supervisor or the owner can see who has a machine's unattended password remembered, and clear it. Nobody ever sees the password.

4b. The free version (V2)

  • Its limits — one person, two computers, unattended only, a password on every computer, and only control, files, copy and paste and printing — are enforced by the server, not by hiding buttons. The hub refuses a third computer when it connects and drops any session message that is not on the free version's allow-list (so a message added to the product later is refused to the free version until somebody decides otherwise). The portal has one rule in front of every page and API, also an allow-list.
  • A free computer is installed with the password typed at the computer, and set by one connection made as that computer, so the agent service still never unlocks itself.
  • With no tray app, the person at a free computer is told by the "Being controlled remotely" bar, for the whole of every session, naming who is connected.
  • The free version's terms say it is for the account holder's own computers only.

5. Keeping companies apart

  • Each IT company has its own separate hub in the server's memory, and every database query is filtered by company. One company cannot see another's customers, machines, tickets or sessions.
  • The tenant key is not a password. It is a long random code (192 bits) that every customer's install needs, so it is public by design — it says "this machine belongs to Anywhere IT". It lets a machine ask for help; it never lets anybody in. Making it longer would change nothing. Do not try to "fix" it.

6. Customer machines

  • Each customer computer gets its own secret device key on first connect. Another computer cannot pretend to be it without that key.
  • A machine that is reinstalled is recognised by a scrambled hardware fingerprint, so its history and customer link are kept rather than it appearing as a new machine. Because any program on a computer can read its hardware fingerprint, **unattended access on a reinstalled machine waits until a supervisor or the owner confirms it is the same machine** (V2.1, HANDOVER.md §111).
  • Files received are checked so they can never be written outside the folder intended. (Four real ways to break out of the folder were found by the test tools and closed.)
  • The host runs with full system rights. That is normal for remote support tools and is what makes password prompts and administrator programs work — but it is a deliberate choice and is why the sign-in protections above matter so much. Scripts also run with full system rights.

7. Stored data

  • Workshop device passwords and email account passwords are stored **encrypted with AES-256** using the server's key folder, data/keys. They are shown only to signed-in staff and only behind a Show button.
  • The key folder is critical. Lose it and every stored password is unreadable. Never change the line SetApplicationName("RemoteSupportPlatform") in Platform/Program.cs — it is part of how those keys work, and changing it has the same effect as losing them.
  • The screen picture is never stored by the server. It only passes through. The exception is a session recording, which a technician chooses to make and which is stored on the server in data/recordings and linked to the ticket.

8. The server itself

Set up automatically by deploy/go-live.sh:

  • Security updates install themselves.
  • SSH (remote login to the server) uses a key only; password login is switched off. Repeated failed logins are blocked by fail2ban.
  • The platform runs as its own limited account (rsp), cannot change its own program files, and only it can read its data folder. Extra Linux sandboxing is switched on.
  • The website sends browser security headers (HSTS so browsers always use https, no framing of pages except website chat, which must be framed to work).
  • Nightly backups of the database and the data folder, encrypted with AES-256, kept for 14 days in /var/backups/rsp. The passphrase is /etc/rsp-backup-key — **without it the backups cannot be opened**, so it must be copied somewhere safe (see document 08). An office PC can fetch each night's copy through an account that can do nothing but list and fetch those encrypted files (rspcopy).
  • The database (PostgreSQL, since 9 October 2026) has no password and listens on no network port: only the platform's own Linux account can reach it, over a local socket.
  • Caddy reaches the platform through a Unix socket that only Caddy and the platform can open; the platform trusts the visitor's address Caddy passes on only when it arrives that way (UnixSocket.TrustCaddy).

8b. The people who run the platform (V2.2)

  • The owner key opens nothing on its own. /owner needs the key and the owner's authenticator code. Two older addresses that answered the key alone were removed on 15 October 2026, and tools/securitycheck fails if they come back.
  • Platform admins sign in to /owner with their own email, password and authenticator, at one of four levels (Viewer, Manager, Full, Owner). Every change they make is logged by name, and **every change to a company goes through one place** (AdminCompanies). An Owner-level admin can never be removed from the pages. Suspending a company now takes effect at once: its consoles and machines are turned away and its people signed out.
  • Keys are never printed. The set-up script says where each key is kept, never the key. If one is ever exposed, deploy\Rotate-Keys.ps1 replaces the owner key and the server key — done on 15 October 2026 after a log containing both was pasted into a chat; the keys in it are dead.
  • Servers talk to each other with a server key, never an admin's password (the control dashboard).

8c. Payments (V2.2)

  • No card number ever reaches our server. The customer types it on PayFast's own pages; we keep only PayFast's token for the subscription.
  • A payment notice is believed only if it comes from PayFast's own addresses, carries a valid signature, names our merchant account and our subscription, and PayFast itself confirms it when asked back. Refused notices are not stored. The account details are put on the server with deploy\Set-PayfastKeys.ps1, never typed into chat or a command line.

8d. Updates (V2.3)

A program that installs other programs on customers' computers is exactly what an attacker would want to control, so the server is never trusted to say what is safe — the signature is. Each computer checks every file of an update itself, with Windows' own signature check, before anything runs:

  • Signed by us: the certificate's organisation must be The Remote Support Program (Pty) Ltd in South Africa, read as fields of the certificate (a certificate anybody makes with our name in it is refused — the test tool proves it). Not "signed by anyone": any company can buy a certificate.
  • Valid and not revoked: if the revocation list cannot be reached, the update waits and tries again.
  • Newer than what is installed: so somebody who took over the server still could not push an old, genuinely signed program with a known fault. Only the computer's own rollback ever goes back.
  • There is no test mode that relaxes any of this.

An update only ever comes from the computer's own IT company's server, and only an agent that says it can update itself is offered one. A release reaches our own company first and pauses itself if computers roll back. See HANDOVER §148.

8e. The outside security review (V2.4)

On 19 October 2026 an outside tester (Daniel) reviewed the live site from outside and signed in as a company owner. They found no way into another company's data and no account takeover. Every finding was checked against the code before anything was changed (HANDOVER §158 — read it before "fixing" any of them again; four were already right and the report could not see why):

  • Fixed: a stranger could keep a person locked out by typing five wrong passwords every 15 minutes. A computer holding that person's trusted for a week sign-in is now counted on its own, so a stranger's failures never lock it. The holding page now sends the same security headers as the platform. 10. Rules for whoever maintains this

  • Never commit secrets to the code repository. The .gitignore file lists what must stay out and why.
  • Run tools/securitycheck after any change to sign-in. It has 78 checks and has proved, by removing each protection in turn, that it notices when one is missing. After a change to unattended passwords run tools/unattendedpw; to the free version, tools/freecheck and tools/freeportal; to removing machines, tools/removecheck.

Restoring from a backup

Backups are .tar.gz.gpg files, encrypted with the passphrase in /etc/rsp-backup-key. Since the move to PostgreSQL each one holds a pg_dump of the database and a copy of the data folder (without recordings, which are backed up one by one). To look inside one on the server:

sudo mkdir -p /tmp/restore
sudo gpg --batch --passphrase-file /etc/rsp-backup-key -d /var/backups/rsp/rsp-YYYYMMDD.tar.gz.gpg | sudo tar -xz -C /tmp/restore

Restoring means stopping the platform, loading the dump into an empty rsp database, copying the data folder back with ownership rsp:rsp, and starting it. A dump restored into an empty database is proved to match the original row by row (tools/backupcheck), but there is no one-command restore script yet: read deploy/rsp-backup.sh (which makes the backup) first, and practise a restore once on a spare server.

If the server is lost completely: build a new one with docs/GO-LIVE.md (about an hour), point the DNS at it in Cloudflare, then restore the latest backup — which you can only do if a copy of the backup and the backup passphrase exist somewhere other than the lost server. 08 — Keys, passwords and accounts

None of the secrets below are on this USB stick. That is deliberate. Anyone holding the secrets could reach every customer computer that allows unattended access, read stored passwords, or take the website down. A USB stick can be copied in seconds without anyone noticing.

How to hand the secrets over safely

Pick one, and write which on the printed copy:

  1. Password manager emergency access (recommended). Most password managers (Bitwarden, 1Password, LastPass, Keeper) let you name a trusted person who can request access to your vault; if you do not refuse within a waiting period you choose, they get it. Put every item below into the vault, and name the trusted person.
  2. A sealed envelope in the same safe, holding the password manager's master password and its recovery code (or a printed emergency kit) — not the individual passwords.
  3. An encrypted file on a second USB stick (for example a 7-Zip archive with AES-256 and a long passphrase), with the passphrase kept somewhere else (the sealed envelope, or a lawyer).

The two most important items are the SSH key (row 1) and the backup passphrase (row 9). With those and this USB stick, a development team can rebuild everything.

13 — What is new in V2.3

V2.2 of this pack was written on 15 October 2026. V2.3 was written on 16 October 2026. One thing was added in that day, and it is a big one: every program now keeps itself up to date. Documents 00–09 have been updated to match; documents 10–12 still list what V2, V2.1 and V2.2 added.

Everything below was built and passed its automatic test tools, but has not yet been tried on real customer computers. The hardware checklist is docs/TEST-3.6.md, sections DD and DE (checks 723–739), and docs/HANDOVER.md §147–§148 is the full engineering record. The plan it was built from, with Clint's decisions, is docs/NEXT-SESSION-AUTOUPDATE.md.

Why it matters

Before this, a customer's computer ran whatever version was installed on it, for ever. Every fix to the programs on customers' computers reached them only when somebody reinstalled by hand — which, with a few hundred machines per IT company, is not a way to run a business. Updating was held back until code signing worked (15 October 2026), because a program that installs other programs on customers' computers must be able to prove they are ours.

Clint's two decisions: customer computers update silently (nobody at the machine is asked), and the rollout is ours alone — an IT company cannot hold its machines back, or a security fix would never reach them.
