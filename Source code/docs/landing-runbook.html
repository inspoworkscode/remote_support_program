Put the landing page live on theremotesupportprogram.com

Create a small Linux server, point the domain at it, and publish a one-page website with Anywhere IT's contact details on it. Everything you need is in the folder this document came in. Allow about an hour, most of it waiting for DNS.

Version 1 · 14 September 2026 Owner: Clint, Anywhere IT queries@theremotesupportprogram.com

The job, in one paragraph

The full product is not being installed yet — it is waiting on two-factor authentication. For now the domain must show a holding page: what the product is, and how to get in touch. You are building the server it will eventually run on, so this work is not thrown away later: the same machine and the same DNS become the real site when Clint is ready.

What is in this folder

Landing-Page-Runbook.pdf  — this document
Publish-Landing.ps1  — the one command you run, from Windows
index.html  — the page itself
go-live-landing.sh  — what runs on the server; you never run this by hand

Copy the whole folder onto the Windows machine you are working from — the Desktop is fine. Do not run it from the memory stick itself if you can avoid it; a stick pulled out mid-upload is an avoidable problem.

1

Create the server at the hosting provider

Create a virtual machine:

  • Ubuntu 24.04 LTS (22.04 is fine too).
  • The smallest size offered is enough for a one-page site. If you are asked to choose and Clint has not said otherwise, pick 2 vCPU / 4 GB — that is what the full product will need when it moves in later, and resizing afterwards is a nuisance.
  • Add your SSH public key during creation, so you can log in as root without a password.
  • Leave the provider's firewall open on 22, 80 and 443.

Write down the public IP address. Everything below calls it <THE-IP>.

Check the login works before going further. The first time it will ask you to confirm the server's fingerprint — type yes:

ssh root@<THE-IP>

Type exit to come back out.

If it asks for a password

Your key did not get attached to the server. Fix that before step 3 — the publish command needs key-based login and will not prompt. Most providers let you add a key and rebuild, or paste one into the console.

2

Point the domain at it in the Cloudflare dashboard

Open the domain in Cloudflare and go to DNS → Records. Change exactly two records:

TypeNameValueProxy status
A@<THE-IP>DNS only (grey cloud)
Awww<THE-IP>DNS only (grey cloud)
Do not touch these
  • The mail records. mail, smtp and webmail, and every MX and TXT record, carry the company's email from a different server on purpose. Changing them stops mail arriving, and it is not obvious for hours that you have done it.
  • The nameservers. DNS hosting is not moving anywhere. Only the two A records above change.
  • The grey cloud. Leave both records on DNS only. Cloudflare's orange cloud stops the certificate in step 3 from being issued.

Changes usually appear within minutes, but allow up to an hour. Check from the Windows PC and do not continue until it answers with the server's IP — the certificate in step 3 cannot be issued before then:

nslookup theremotesupportprogram.com
3

Publish the page on the Windows PC

Open PowerShell in the folder you copied (right-click the folder while holding Shift → Open PowerShell window here), and run this, with the real IP in place of <THE-IP>:

powershell -ExecutionPolicy Bypass -File Publish-Landing.ps1 -Server <THE-IP>

That uploads the page and sets the server up. It prints the phone number and links it is about to publish, so you can see they are right before it finishes. On the server it:

  1. installs Caddy, the web server;
  2. copies the page to /var/www/landing;
  3. gets a TLS certificate for the domain and www, automatically;
  4. closes the firewall to 22, 80 and 443 only;
  5. fetches the site and tells you the result.

The last line should read https://theremotesupportprogram.com -> HTTP 200 followed by Live.

If it is not 200

Nearly always DNS. Caddy has to be reachable on port 80 at the domain name before a certificate can be issued. Re-check step 2, give it a few minutes, and watch the certificate arrive with:

ssh root@<THE-IP> "journalctl -u caddy -f"

Press Ctrl+C to stop watching. Once DNS is right, this fixes itself without you re-running anything.

Running it again is safe

If Clint asks for a wording change, he edits index.html and you run the same command again. It takes a couple of seconds the second time — Caddy and the certificate are already there.

If the script will not run at all

Only if PowerShell refuses and you cannot get past it. This does the same thing by hand, but the contact details will be missing from the page — the script is what fills them in. Tell Clint if you have to do it this way. The address at the end is not a typo: that is who the certificate is registered to, which is Clint himself, not the enquiries mailbox on the page.

scp index.html go-live-landing.sh root@<THE-IP>:/tmp/
ssh root@<THE-IP> "cd /tmp && sed -i 's/\r$//' go-live-landing.sh && chmod +x go-live-landing.sh && ./go-live-landing.sh theremotesupportprogram.com clint@anywhereit.co.za"
4

Check it from a phone, not the PC you worked on

  • https://theremotesupportprogram.com loads, with a padlock and no warning.
  • https://www.theremotesupportprogram.com does the same.
  • The page shows 078 131 5618 and queries@theremotesupportprogram.com.
  • Tapping the phone number offers to call it.
  • Tapping WhatsApp opens a chat to that number with a message already typed.
  • Tapping Ask for more information opens a new email to Clint.
  • It reads properly on a phone screen — nothing cut off, no sideways scrolling.
Why a phone

The phone and WhatsApp links are the whole point of the page, and they only really work from a phone. A desktop browser will not prove they are right.

Hand back to Clint

  • The server's public IP, and which provider and account it was created under.
  • Confirmation that both addresses load with a valid padlock.
  • Confirmation that the phone, WhatsApp and email links were tested from a real phone.
  • Anything in the checklist that did not pass.
  • The monthly cost of the server, if you chose the size yourself.

What happens later — not part of this job

When two-factor authentication is finished, Clint runs a different command from his own machine that turns this same server into the full product: the website, the customer portal and the remote support service. That replaces what the web server hands out — same server, same certificate, same DNS, no gap where the domain is dead.

So do not
  • delete or rebuild this server when you are finished with it;
  • install anything else on it, or use it for another customer;
  • change the DNS records again.

Useful commands
